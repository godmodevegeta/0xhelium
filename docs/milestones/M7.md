# M7 — Independent regression gate and policy promotion

Status: **implemented and evaluated once locally; awaiting review; not merged, not deployed.**
The pre-registered gate `gate-v1` evaluated the five M6 reflex candidates once against data M6
never used for tuning. The primary candidate `cand-ea7b9dbc0bbd` passed all four criteria and the
policy registry now points at `v1-cand-ea7b9dbc0bbd`. That version is the frozen `go1-walk-s0`
weights, unchanged, plus a bounded 10-parameter residual reflex. It is not PPO, the network was
not fine-tuned, and the result does not mean the robot is robust in general. The primary also has
16 individual regressions, all in low-friction conditions (details below).

## Pre-registration

code ran on any locked episode. It pins, by SHA-256: the base policy, the M6 reflex calibration,
the M6 hardening-sets file (locked split `599888a34071…`), and the five candidate records. It also
fixes every episode of every suite, the criteria with their thresholds, the statistical test, and
the primary candidate.

**Once only.** `robustlab gate` refuses to evaluate when the config, a candidate record, the
calibration, the policy or the locked set does not match its hash. It also refuses when a result
already exists in `runs/m7/gate-v1/` or `presets/m7-gate-v1/`. A second run was attempted after
the evaluation and was refused. `--verify` recomputes the result without writing anything; with 4
workers it reproduced `results_sha256 f3d26d3d3d20…` exactly. A new gate needs a new version and a
new locked set.

## Suites

Every suite runs on the baseline (zero residual) and on all five candidates. Episodes are
deterministic, so "paired" means the same episode under both controllers.

| Suite | Episodes | What it is | Role |
| --- | ---: | --- | --- |
| Locked holdout | 10 | The 10 locked M6 attacks (M4 discovery finals, M3 150 N, M5 μ 0.3, M2 100 N timings), evaluated for the first time | G2 |
| Nominal walking | 13 | 3 locked nominal walks (turn right, fast, 5 kg top) + 10 gate-defined walks: 10 s forward, 10 s zero command, sidestep left, backward, μ 0.1, 0.2, 1.5, 5 kg forward, 5 kg left, μ 0.3 + 3 kg | G1 |
| Regression gauntlet | 1280 | 5 conditions × every 4 ms shove start in [2.000, 3.024) s, toward the right for 0.1 s: 100 N, 150 N, μ 0.3 at 100 N, 3 kg at 100 N, μ 0.3 + 3 kg at 100 N | G3 |
| Known failures | 34 | The confirmed M4 discovery finals | reported only |

The gauntlet contains the M6 training and validation timings. It detects regressions; it is not
independent evidence of improvement. The known failures include M6 training data, so they are
not a criterion.

## Criteria (all must pass)

| | Criterion |
| --- | --- |
| G1 | Nominal: 0 falls and 0 numerical failures on every nominal episode, and final displacement in the initial-heading frame within max(0.10 m, 10%) of the baseline's |
| G2 | Holdout: fewer falls than the baseline, fall rate ≤ max(0.50, baseline rate − 0.25), and exact one-sided McNemar p ≤ 0.05 on the paired outcomes |
| G3 | Gauntlet: fall rate ≤ baseline + 3 percentage points overall and in each of the 5 conditions; every individual regression is listed |
| G4 | 0 numerical failures in any suite |

## Registry

`policies/registry/`, written only by `gate.registry.apply_decision`:

- `versions/v0-baseline.json` is the frozen `go1-walk-s0` with no reflex.
- `versions/v1-cand-ea7b9dbc0bbd.json` is immutable. It records the parent `v0-baseline`, the
  candidate record and its hash, the gate name, the gate `results_sha256`, and that the policy
  weights are unchanged.
- `active.json` is replaced atomically. It holds `v1-cand-ea7b9dbc0bbd` and the history v0 → v1.
- `rejected/` would hold rejection records. No rejection was recorded: only the primary was
  eligible, and it passed.

At startup the API checks that the gate result matches its preset hash and the gate config. It
also checks that the promoted registry version cites the same `results_sha256`. It refuses to
start on a mismatch, and a unit test covers a tampered preset.

## Application

- `GET /api/gate` returns the decision and the per-candidate criteria. It includes holdout rows for
  every controller, nominal rows, gauntlet conditions with every regression, known-failure counts,
  the registry state and provenance. It does not include the full 3 MB per-episode outcomes.
- `GET /api/gate/replay?candidate=&episode=&ghost=baseline|matched` re-simulates any gate episode
  for the baseline and a registered candidate, locked episodes included. The gate result now
  exists, so replays cannot influence it. The replay re-runs both controllers exactly as they were
  recorded (stopping at the first fall for attack suites) and compares outcome, fall time and
  trajectory digest. In the API tests, digests matched for a holdout attack and a nominal walk.
  Manual checks also covered a gauntlet regression and a known failure (0.2–0.5 s per replay).
- The baseline-vs-reflex replay is now one shared function (`api/reflex_replay.py`) used by the
  Hardening and Gate APIs. The Hardening API still refuses locked episodes.
- The **Harden** mode's status pill shows the gate verdict for the candidate shown:
  - "Promoted by gate-v1 as v1-cand-ea7b9dbc0bbd" for the precomputed sample, which is the
    primary;
  - "Candidate · not evaluated by the regression gate" for a newly run candidate.

  Candidate ids are content hashes, so an equal id means equal inputs.
- The **Results** mode has a "Regression gate · M7" summary and evidence sections:
  - decision and registry;
  - criteria for any of the five candidates;
  - holdout table;
  - gauntlet with regression replays;
  - nominal table, with reflex activity above 25% highlighted;
  - all candidates;
  - provenance.
- **Stress test**, **Discover failure** and **Design scenario** still evaluate the frozen baseline
  v0 and say so, so their results stay comparable with M2–M5. The footer says that only the gate
  moves the registry pointer.

**Label fix found by the new checks.** In 2 of 3 repeated scans, the mobile Harden replay drew the
wider "FELL" ghost label partly outside the canvas for 3–4 frames. Labels were only placed on the
next animation frame after React changed their text. They are now also placed in a layout effect
after each commit. Afterwards, 5 repeated runs of all 8 label scans showed 0 overlaps and 0
frames outside the canvas.

## Limitations

- **Small holdout.** There are 10 locked attacks with correlated conditions, several of them close
  in timing. The candidate's Wilson interval is [10.8%, 60.3%]. The improvement is significant
  for these 10 paired episodes. It does not estimate the fall rate for shoves in general.
- **Individual regressions.** The aggregate G3 rule tolerates up to 3 points per condition. The
  promoted version is worse than the baseline at 16 specific low-friction timings. A deployment
  with per-case requirements would reject it.
- **Nominal gait changes.** The reflex is active on most ticks of the payload walks. The tolerance
  is on displacement only, not on gait, energy or joint loads.
- **The gauntlet overlaps M6 training timings.** Its improvements (100 N, 150 N) are partly
  in-sample.
- **One simulator.** The results hold for flat ground with uniform friction, an idealized trunk
  force, a welded payload box, the pinned MuJoCo 3.15 and this CPU. There is no sim-to-real
  claim.
- **Unchanged modes.** The registry pointer moved, but the Stress, Discover and Design modes still
  run v0 by design. Running v1 there would need new presets and is not part of M7.
- **Documentation-sync hook.** `PostTaskExec` did not fire, because `tasks.md` was edited directly.
  This file, the README and the build log were updated by hand.
