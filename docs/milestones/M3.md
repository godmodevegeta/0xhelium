# M3 — Web application with 3D replays

Status: **implemented and measured locally; awaiting review. Not deployed.** A FastAPI backend serves
two presets and a React/Three.js viewer that replays recorded MuJoCo trajectories. Preset 1 shows the
exhaustive M2 sweep and replays any timing. Preset 2 runs real 16-trial experiments on request.

Spec: `.kiro/specs/web-replay/`. Branch `m3-web-replay`, from `main` after the M2 merge (`451fef8`,
merge of `m2-baseline` = `64165ea`). One writer. Backend code measured at `3723669`; the viewer
was added in `57b25a9` with no backend change.

## Run it

```bash
uv sync --extra server
(cd web && npm ci && npm run build)
uv run robustlab serve            # http://127.0.0.1:8000
```

Development: `uv run robustlab serve` plus `cd web && npm run dev` (Vite proxies `/api`). Deep
links: `/?replay=500` opens the failure replay, `&frame=103` starts at a frame, and
`/?tab=live&run=<run_id>` opens a live run.

Cold start from a fresh clone (`git clone`, `uv sync --frozen --extra server`, `npm ci`,
`npm run build`) took 5 s with warm package caches. The server then returned `/` 200 and the
hidden-phase summary (11/256), and its replay of 2.000 s re-simulated with matching digests.

## Choosing the Live Stress force

Bounded sweep with the M2 runner (`scripts/force_sweep.py`, recorded at `c682baa`). Only the force
changes: 0.1 s toward the robot's right, 1 m/s, `fall-contact` scene, start times in
[2.000, 3.024) s. For each force: the exhaustive 256-start grid, and the 16-trial stratified suite
with the M2 example seed 20261121. The last three columns are computed exactly from the exhaustive
grid: the distribution of a 16-trial stratified count, given each stratum's measured failure
fraction.

| Force | Exhaustive falls | 16-trial, seed 20261121 | P(0 falls in 16) | P(mixed) | Most likely count |
| --- | --- | --- | --- | --- | --- |
| 100 N (M2) | 11/256 = 4.3% | 0/16 | 0.478 | 0.522 | 0 |
| 110 N | 32/256 = 12.5% | 3/16 | 0.065 | 0.935 | 2 |
| 120 N | 45/256 = 17.6% | 3/16 | 0.014 | 0.986 | 3 |
| 130 N | 53/256 = 20.7% | 3/16 | 0.004 | 0.996 | 3 |
| 140 N | 56/256 = 21.9% | 3/16 | 0.002 | 0.998 | 4 |
| 150 N | **65/256 = 25.4%** | 3/16 | 0.0003 | 0.9997 | 4 |

All falls at every force are `tilt` falls, and there are no numerical failures.

**Choice: 150 N.** It is the only tested force whose exact frequency lies in the requested 25–75%
band, just above its lower edge. It is also the 150 N upper bound of the M1 push envelope, so no
higher force was tested. A 16-trial run at 150 N shows a mix of falls and survivals in 99.97% of
seeds. The preset was chosen from the exhaustive frequencies, not from any particular 16-trial
outcome. The stored seed 20261121 happened to give 3/16 at every force from 110 to 150 N, because
the same timings are drawn each time.

**The response is not monotonic per timing.** The overall frequency rose with force across these
five forces, but individual timings flip back:

| Force step | Timings that fell at the lower force but survived at the higher |
| --- | --- |
| 100→110 N | 2 |
| 110→120 N | 0 |
| 120→130 N | 1 |
| 130→140 N | 4 |
| 140→150 N | 5 |

At 140 N and 150 N, falls also appear outside FR+RL stance: 1/25 "no foot down" at 140 N, and 1/25
"no foot down" plus 1/96 FL+RR at 150 N.

## Preset 1 — Hidden Phase Vulnerability (precomputed)

`presets/hidden-phase-v1/experiment.json` is the M2 report `runs/m2/grid-all-256` (commit
`0b57e70`, `results_sha256 66df5556…`). The backend checks its SHA-256 against `preset.json` on
start and never reruns the 256 trials.

- Headline: **11/256 shove timings fell (4.3%)**, labelled "Precomputed · M2 exhaustive sweep ·
  commit 0b57e70".
- Sweep chart: all 256 start times coloured by outcome, with a stance band underneath. Any bar can
  be selected to show its outcome, stance, first fall time, time after the shove, events, first
  non-foot body and progress.
- Finding shown as measured: all 11 falls were in FR+RL stance, but only 11 of the 110 FR+RL timings
  fell.
- **"Replay a failure"** uses 2.000 s, the M1 timing. Replaying any timing **re-simulates that one
  paired trial** through the same `run_trial` function the suite uses, then compares both trajectory
  digests and outcomes with the record. The badge says "Re-simulated now · matches recorded M2
  result" or flags a mismatch. The integration test requires a match at 2.000 s (fell) and 2.004 s
  (survived). A re-simulation takes 0.15–0.16 s; repeat requests are served from a 32-entry cache
  in 5 ms.

## Preset 2 — Live Stress Test (executed now)

"Run 16 Trials" posts to the backend, which draws a fresh seed (or uses the one typed), writes
`request.json`, and runs `run_suite` with the preset config on the experiment worker. The viewer
polls progress, fills 16 chips as trials finish (green survived, red fell, purple numerical), and
shows falls over valid trials, the Wilson interval, the seed and the reproduce command. Each chip
opens that trial's recorded trajectories. A precomputed reference card shows 65/256 at 150 N.

## Replay

The server computes poses; the browser only draws them. For every recorded `qpos` row (frame 0 =
reset state, then one frame per 20 ms Tick), `mj_kinematics` gives the world pose of the 13 visual
geoms. Meshes come from the compiled model (`mesh_vert`, `mesh_face`), so they share MuJoCo's
recentred mesh frames; a test checks the poses against `mj_forward` to 1e-12 m.

The viewer shows both robots in one scene on one clock: shoved robot opaque, nominal robot
translucent blue. Playback controls are play/pause, scrub, 0.1–1× speed and "jump to shove". The
shove is drawn as an orange arrow during its active interval, coming from the side it pushes from.
The timeline marks the shove interval, every fall event (first one emphasised) and non-foot contact
Ticks. Readouts show time, tilt, trunk height, feet down and non-foot contact.

Screenshots (headless Chrome, SwiftShader WebGL) are in `runs/m3/screens/`:
- `hidden-phase.png`: preset 1;
- `replay-500-frame103.png`: shove arrow at 2.06 s;
- `replay-500-frame150.png`: the shoved robot on its back at 3.00 s while the nominal robot walks on;
- `live-stress.png`: the first live run, 4/16.

## What this establishes, and what it does not

- The web results are the M2 runner's results. Preset 1 numbers are the committed M2 record.
  Replays re-run the same code and show whether they matched. Live runs execute the experiment
  and can be regenerated from their seed.
- At 150 N toward the robot's right, 65 of 256 shove timings fall (25.4%) in this simulation, and
  live 16-trial runs gave 4/16, 5/16 and 4/16. As in M2, this describes only that timing
  distribution with everything else fixed. It says nothing about the real robot or other
  disturbances.
- 150 N is at the edge of the requested band and at the force cap. The "around 25–75%" target was
  met only at 25.4%, not in the middle of the band.

## Limitations

- **Not deployed.** `delivery.md` M3 asks for a public beta URL. That needs a hosting choice and
  credentials, so it is still open. The server binds to 127.0.0.1 and has no authentication or
  rate limits.
- **Job state is in memory.** Run directories are durable, but a run interrupted by a restart shows
  as `incomplete`.
- **The mesh payload is 2.1 MB gzipped** on first load; the browser does not cache it under a
  content hash yet.
- **No automated browser interaction tests.** UI checks are typecheck, build and headless
  screenshots.
- **Playback is nearest-frame at 50 Hz.** Before the shove the two robots overlap exactly, by
  construction.
- **Fixed after review: playback did not advance at speeds below about 1.5×,** including the
  default 0.5×. Each rendered frame recomputed time from the rounded frame index, so the fraction
  of a frame gained per render was rounded away (0.5× at 60 Hz adds 0.42 frames per render). The
  playhead is now a continuous time in seconds. Checked in headless Chrome after 60 s of virtual
  time on `/?replay=500`: the old build still showed t = 0.06 s, the fixed build t = 1.38 s and
  advancing. Play at the last frame now restarts from the beginning.
- **Pairing statistics are not shown per trial in the UI** (they are in `experiment.json`).
